# City Brain: graph module (report paragraph)

**What.** The graph module is the Brain's memory. It holds the city map (zones, sensors, actuators, units and their links) and every event of the Brain, linked together: abnormal readings, Guardian verdicts, calls, incidents, proposals, decisions, actions and acknowledgements. A small HTTP API answers the questions the other modules need: the context of an incident for the LLM, a zone or its actuators for scoring and output, and the full chain of an event for the timeline and this report.

**How.** The graph is an in-memory property graph written with the Python standard library. It has typed nodes and named links such as `NEXT_TO`, `IN`, `CONTROLS`, `FROM`, `ON`, `EVIDENCE`, `FOR`, `CHOSE`, `EXECUTES`, `TARGETS` and `CONFIRMS`. Every event node is indexed by its `correlation_id`, the id of the external message that started the chain. So `GET /chain/{id}` returns reading, verdict, incident, proposals, decision, action and acknowledgement in order. An acknowledgement carries the Brain command id, so it is linked through the action that holds that command. Normal readings are not stored: the sensor node keeps its latest value, and a ring keeps the last few thousand readings. A reading becomes a node only if it is at alert level, if Guardian rejects or suspects it, or if an incident uses it as evidence. Each kind of node has a cap, and the oldest is dropped with its links. `GET /context/{incident_id}` returns the incident, its evidence, the neighbouring zones and the actuators that act on them (with state and quarantine), the free units, the quarantined devices, and the related events of the area in the last 15 minutes. Lists are trimmed until the JSON fits in 1,500 characters. The graph also carries an incident history from a real storm: the 6,273 NYC 311 calls of Hurricane Ida (2021). An offline tool cleans them, measures for each call how many similar calls came city-wide in the previous hour (five surge levels), finds the surge waves (three, of 7 to 15 hours, peak 659 flood calls per hour) and measures that traffic signal failures ran 5.4 times higher during the waves. For a live flood, `/context` adds a one-line hint matched on the incident's severity, and the same data loads into Neo4j to explore the storm as a graph.

**Why.** The Brain needs a few fixed questions answered in milliseconds on a laptop. It does not need a query language, so a dictionary-based graph avoids running a Java database next to the LLM. The same links that answer the questions also give the audit trail: any command can be traced back to the readings and calls behind it. Storing only meaningful readings keeps memory bounded over a long scenario. The context is kept short because it goes straight into the LLM prompt. The history is matched on incident type and surge level, which is what a vector search over the notebook's templated sentences returns, so the Brain needs no vector database, model download or network during the demo.

**Limits.** The graph lives in memory. A restart loses the history, but the retained topics give back the city map, trust and quarantine at once. There is no query language: each new question needs a new endpoint. Readings older than the ring cannot be promoted later. The API has no authentication and listens on 127.0.0.1 only. It must not be exposed beyond the Brain host. The `GET /graph` view is a JSON export for a visualization, not an interactive graph browser. The history comes from another city and storm, covers floods only, and maps severity to surge level by configuration; the LLM uses it only once its prompt has been re-benchmarked with it (`use_history`).
